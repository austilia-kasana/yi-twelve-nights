# 运输时间模型（设计稿）

> 状态：**设计阶段，未实现。**
> 这份文档要解决的问题：现在的「行程夜数」是假的——一封信写着「需要 2 夜」，
> 骑手下一夜立刻可用。于是「路远」没有任何代价。

---

## 0. 为什么必须改

三个已经观察到的现象，根子是同一个：

1. **旧矿道在暴雪天既最快又最安全**（等效距离 5.00 vs 北口 10.00、河渡 5.71）
2. **「只接有余量的」比「赌预报」S 率高 14 个百分点**——保守不付任何人力代价
3. 玩家感觉不到「押上这趟，人就回不来了」

**当前模型**：`nights` 只是一个和 `deadline` 比大小的数字。
1 夜和 3 夜的行程，占用骑手的时间完全一样。

---

## 1. 两份评审的分歧，和我的取舍

| 议题 | 哈基米 | 龙娘 | 我的选择 |
|---|---|---|---|
| 在途期间天气 | 出发夜锁定，之后不管 | 每夜推进，受当夜天气影响 | **龙娘** |
| 送达 vs 返程 | 没提 | 建议分成 delivery_eta / return_eta | **折中**：不设独立返程阶段 |

### 为什么选「每夜天气」

现在的模型在物理上就是错的——用**出发夜一晚上的天气**决定整趟 2 夜的行程。
修在途会逼我们直面这个错误。

哈基米担心「UI 倒计时会绕」是对的，但解法不是取消它，而是：

> **不显示精确 ETA，显示「预计 2~3 夜」。**

这本来就更符合「预报只有七成准」的世界观。

### 为什么不设独立返程

龙娘建议分出 `return_eta`。**但那样 2 夜去 + 2 夜回 = 骑手离开 4 夜，
吞吐直接砍到 1/4。那不是策略深度，是瘫痪。**

我的做法：**骑手「到达那夜」仍算占用，下一夜才可用。**
这样既没有「送到就瞬移回驿站」的逻辑漏洞，也不会把吞吐砍死。

## 2. 数据模型

### 新增 `ActiveTrip`

```python
@dataclass
class ActiveTrip:
    dispatch: Dispatch
    rider_id: str
    horse_id: str
    route: str
    distance: int          # 出发时锁定（修路会影响，所以出发那一刻定）
    progress: float        # 已推进的等效距离
    depart_night: int
    trips_history_note: str = ""
```

**由 `GameState.trips: list[ActiveTrip]` 统一管理。**

龙娘这条建议是对的：不要在骑手、马、任务三处各维护一套状态。
骑手和马只需要知道「我是不是在途」，具体在哪由 `GameState.trips` 反查。

### 状态字段

| 对象 | 现状 | 改动 |
|---|---|---|
| `Rider.state` | `"idle" / "injured"`（`"out"` 声明了但从未使用） | 启用 `"out"` |
| `Horse.state` | **没有这个字段** | **新增** `"idle" / "out"` |

`Rider.is_available()` 已经是 `state == "idle"`，所以设成 `"out"` 自动就挡住派单。
`Horse` 要加同样的判断。

## 3. 每夜循环

`advance()` 改成三阶段：

```
① 推进所有在途任务
     for trip in self.trips:
         trip.progress += 该队本夜的推进量（用当夜真实天气）

② 结算到达
     凡是 progress >= distance 的，判定送达/超时，扣赏罚，可能受伤
     从 self.trips 移除

③ 处理今晚的新派单
     扣体力/马状态/油；state = "out"；加入 self.trips
```

### 推进量

```python
推进量 = rider.effective_speed()
       * horse.effective_speed()
       * 当夜天气系数[route]
       * 灯系数
       * BASE_TRAVEL
```

和现在的 `travel_nights()` 是同一个公式，只是从「一次算总时间」变成「每夜加一格」。

### 一个具体的例子

```
第 5 夜（预报晴，实际晴）：
  老陈 + 乌蹄 → 旧矿道（距离 5）
  推进量 = 1.15 × 1.10 × 1.00 × 1.00 × 2.0 = 2.53
  progress = 2.53 / 5      → 未到

第 6 夜（预报晴，实际暴雪）：
  推进量 = 1.15 × 1.10 × 1.00（矿道免疫）× 2.0 = 2.53
  progress = 5.06 / 5      → 到达，结算

老陈第 7 夜才能再用。
```

**注意**：矿道天气免疫，所以暴雪不影响它——这符合「矿道稳」的设定。
但**它仍然要占用 2 个夜晚**，这就是新的代价。

## 4. 关键规则（每条都要有测试）

### R1 · 骑手何时释放

> 距 5、推进量 2.53/夜 → 第 5 夜出发，第 6 夜到达，**第 7 夜可再用**。

**测试**：`两夜任务真的占用两个回合`

### R2 · 出发夜扣什么

- 扣体力（`STAMINA_COST_MIN..MAX`）
- 扣马状态（`HORSE_COST_MIN..MAX`）
- 扣油
- `state = "out"`

### R3 · 在途不恢复

骑手 `state == "out"` 期间**不回体力**；马 `state == "out"` 期间**不回状态**。

（这条是哈基米强调的，现在的代码是按「今晚有没有被用」判断，改成按 state。）

### R4 · 事件什么时候抽

**每夜抽一次推进事故，还是整趟抽一次？**

我的选择：**每夜抽，但频率按「每夜」重新标定。**

现在的 `EVENTS` 权重是「每趟一次」的。如果直接套到每夜，
一趟 3 夜的行程出事概率会变成 1-(1-p)³，**长途会变得不可用**。

**所以 Phase C 要重新标定事件权重**，大致原则：
```
每夜事故概率 ≈ 原来每趟概率 / 平均行程夜数
```

### R5 · 第 12 夜还在途怎么办

**算失败，但日志写明原因。**

```
[败] 老陈 旧矿道 八百里：信还在路上，十二夜就结束了。
```

不扣罚（信没丢，只是晚了），但也不算送达。

**测试**：`最后一夜仍有任务在途时如何结算`

### R6 · 在途任务存档

`ActiveTrip` 要进 `to_dict()`，`SAVE_VERSION` 升到 **3**。

**测试**：`在途任务读档后是否继续正确推进`

### R7 · 修路与在途

已经出发的任务，`distance` 在出发时锁定，中途修路不影响它。

## 5. 已知的平衡冲击（Phase C 要处理）

**吞吐量会掉。** 粗略估算：

```
现在：骑手 55% 出勤 → 2 人 ≈ 1.1 趟/夜 → 12 夜约 13 趟
改后：平均行程 2 夜 → 出勤掉到约 30% → 约 7 趟
```

信收入从 +45 掉到约 +24 → 终局信约 74，**S 线 80 摸不到，达标线 60 也边缘**。

**所以要动这些：**

| 参数 | 现在 | 可能要改成 |
|---|---|---|
| `FAITH_PER_DELIVER` | 2.8 | 4.5~5.0 |
| `STAMINA_COST_MIN/MAX` | 24/40 | **12/20** |
| `REST_STAMINA_GAIN` | 35 | 可能不用动 |

### 关于体力：我和自己讨论过的一个问题

**在途和体力会重复惩罚同一件事。**

现在一个骑手不能去的理由是「体力低」。加了在途之后，多了「他还没回来」。
对长途来说这是两次惩罚。

**我的方案：大幅降低体力消耗（32 → 16 左右）。**

理由：体力负责「别让同一个人连跑三夜」，在途负责「长途要付时间」。
两个机制各管一件事，不抢同一个角色。

**但这会让游戏更简单还是更复杂？我不确定，需要在 Phase C 用模拟验证。**

## 8. 我还没想清楚的两件事

### ① 玩家怎么知道「今晚天气变坏了，在途那队会慢」

需要在 UI 上显示：
```
老陈 → 北口   已走 60%   按今晚天气还要 1 夜
```

**但「还要 1 夜」又是根据当晚天气算的，而明晚天气未知。**
所以只能显示「已走 60%」，剩下的让玩家自己判断。

### ② 多头在途时，日志会不会淹没

如果同时有 3 队在途，每夜每队一行日志，那 12 夜会刷爆。
可能要合并成一行：「在途 3 队，进度 40%/60%/20%」。
