## 0. 要解决的问题

现在的「行程夜数」是假的：一封信写着「需要 2 夜」，骑手下一夜立刻可用。
于是「路远」没有任何代价。

三个已经观察到的现象，根子是同一个：

1. 旧矿道在暴雪天**既最快又最安全**（等效距离 5.00 vs 北口 10.00、河渡 5.71）
2. 「只接有余量的」比「赌预报」S 率高 14 个百分点 —— 保守不付人力代价
3. 玩家感觉不到「押上这趟，人就回不来了」

---

## 1. 时间轴（定案）

**以第 N 夜为玩家当前正在安排的夜晚。**

```
第 N 夜     派出 → 当夜推进第一次 → 夜末若已走完则抵达
第 N+1 夜   继续推进 → 抵达（两夜任务）
第 N+2 夜   人马归队，可以重新派遣
```

| 行程 | 抵达 | 可再用 |
|---|---|---|
| 一夜任务 | 第 N 夜 | 第 N+1 夜 |
| 两夜任务 | 第 N+1 夜 | 第 N+2 夜 |
| 三夜任务 | 第 N+2 夜 | 第 N+3 夜 |

**抵达夜仍然算占用。** 人马要到「抵达夜的下一夜」才归队。

### 阶段顺序（定案）

```
① 校验并登记本夜新派单，扣除出发资源
② 推进所有在途任务，**包括刚刚出发的**
③ 统一结算抵达，释放人马
```

**为什么顺序是这个**：玩家安排的是「当前夜的派遣」，当前夜的天气就应该参与推进。
如果新任务从次夜才开始推进，整体会晚一夜，和示例对不上。
（这条是哈基米指出的原稿矛盾，龙娘定案。）

### 必须写成测试的

- `一夜任务：出发当夜抵达，次夜可用`
- `两夜任务：出发次夜抵达，再下一夜可用`

**不要再出现「一夜任务出发次夜才抵达」这种表述。**

## 2. 资源语义（定案）

| 项目 | 规则 | 时机 |
|---|---|---|
| 骑手体力 | 扣 `STAMINA_COST_MIN..MAX` | **出发时一次性** |
| 马的状态 | 扣 `HORSE_COST_MIN..MAX` | **出发时一次性** |
| 油 | 扣 `4..8` | **出发时一次性** |
| **灯火系数** | **出发时锁定，整趟不变** | 出发时 |
| **天气系数** | **每夜重新计算** | 每夜 |
| 油量后续变化 | 不影响已出发的任务 | — |
| 体力/状态恢复 | **在途期间不恢复** | — |

`ActiveTrip` 必须有 `light_factor: float` 字段。

**为什么灯火锁定而天气不锁**：油是出发时一次性扣的，不是每夜扣。
如果第二夜驿站油烧光了就让第一夜已出发的队伍突然减速，那资源语义就不自洽了。
天气不同——天气本来就每夜变，它作用于「今晚走了多远」。

（这条是哈基米提出、龙娘拍板的。）

## 3. 数据模型（定案）

### `ActiveTrip`

```python
@dataclass
class ActiveTrip:
    dispatch: Dispatch
    rider_id: str
    horse_id: str
    route: str
    distance: float          # 出发时锁定（修路不影响已出发的任务）
    progress: float = 0.0
    depart_night: int = 1
    elapsed_nights: int = 0
    due_night: int = 1       # 绝对夜数，随存档保存
    light_factor: float = 1.0
    events: list = field(default_factory=list)
    id: str = field(default_factory=lambda: _next_id("t"))
```

**`due_night = depart_night + deadline - 1`**，随存档保存，不每次重算。

### 状态归属（定案）

**`ActiveTrip` 是「谁在途」的唯一事实来源。**

```python
Rider.state   →  只有 "idle" / "injured"（**不再有 "out"**）
Horse         →  **不加 state 字段**
```

可用性由 `GameState` 查询：

```python
def is_busy(self, rider_id=None, horse_id=None) -> bool
def available_riders(self) -> list[Rider]
def available_horses(self) -> list[Horse]
```

**为什么不在人马身上也存 `out`**：那就是两份状态。
任务若因遇劫提前结束，忘了把 `out` 改回来，就会出现失联状态；
存档恢复时也只恢复一处。单一事实来源从根上消灭这类 bug。

**代价**：`Rider.is_available()` 不能再单独判断可用性，必须走 `GameState`。
`relay/ui/scenes.py` 和 `tools/ai.py` 都要同步改。

## 4. 抵达判定（定案）

```
抵达夜晚 <= due_night  →  送达成功，加赏、加信
抵达夜晚 >  due_night  →  超时失败，扣罚
```

**关键规则（龙娘补充，我和哈基米都漏了）：**

> **期限决定信件能否成功，不决定运输任务什么时候结束。**

**即使已经超期，人马仍然保持在途，直到这趟任务抵达。** 不会瞬移回驿站。

**为什么**：否则「信件超时」这个判定会同时决定「任务终止」，
而这两件事在物理上无关。信件晚到了，人马也得走完才回得来。

## 5. 事件（Phase B2，本阶段不实现）

**B1 只保留「无事」。** 事件系统单独做，不要同时重写时间模型和事故系统。

（理由：出了问题无法定位是哪个改动的锅。）

B2 的候选效果（未定案）：

| 事件 | 每夜效果候选 |
|---|---|
| 顺风 | 本夜进度 × 1.5 |
| 迷路 | 本夜进度 × 0.5 |
| 落石 | 本夜进度归零 + 该任务距离 +1 |
| 遇劫 | 信件丢失，任务立即结束，人马下一夜归队，骑手受伤概率提高 |

**概率换算不能是 `p / N`**，应该是：

```
p_night = 1 - (1 - p)^(1/N)
```

否则累计事故概率对不上。

## 6. 受伤（定案）

**抵达时受伤**：

- 骑手从任务中释放，但**变 `injured`，不是 `idle`**
- **伤势倒计时不在本夜立即减少**（沿用现有的 `injured_tonight` 保护逻辑）
- 这条不能因为换成 `ActiveTrip` 就丢掉

**在途期间**：不会受伤（受伤只发生在抵达结算时）。

---

## 7. 信归零（定案）

多队同夜抵达时，**按稳定的任务 ID 顺序结算**，每结算一队检查一次 `faith`：

```
faith > 0  →  继续结算下一队
faith <= 0 →  停止后续所有奖励、罚款和事件结算，结束游戏
```

**尚未抵达的任务终止，不再产生奖励。**

**但已经在本夜派出的任务，资源不退还。**

**为什么这么定**（龙娘对哈基米的修正）：玩家是在**夜初**决定派遣的，
任务已经出发，夜末才可能因为其他队伍结算导致信归零。
**不能假装这些新任务从来没有派出去。**

---

## 8. 第十二夜（定案）

**第十二夜结束时仍未抵达的任务，按未送达处理：**

- 扣除一次正常罚款
- 不获得奖励
- **计入总派遣数和送达率分母**

**这是十二夜战役结束造成的最终超时，不代表信件遗失。**

### 为什么不用「不扣罚」

原稿规定第十二夜在途 = 失败但不扣罚，那是一个**免费期权**：
最后一夜把所有人马撒出去，成功拿赏、失败不亏。

### 第十二夜还接受新派遣吗

**接受**，但受第 8 条约束：一定按正常罚款结算。

（最初的方案是「禁止无法在本夜完成的派遣」，但那样会让最后一夜空着，
而且和「超期继续运输」的规则不一致。改成「照常派、照常罚」更简单。）

## 10. 确定性（定案，必须保留）

v0.3.0 修好的两个公平性机制，新模型必须继续保留：

1. **灯火系数在夜初统一算一次**，同一夜所有新派单用同一个快照
2. **所有结算按稳定 ID 排序**，不能让列表插入顺序决定谁先抽到事件

第 2 条要扩展：**多个在途任务每夜同时推进时，也要按任务 ID 排序。**

## 11. UI 和日志（Phase C）

**UI 不展示精确 ETA**（依赖未来未知天气，是假的）：

```
老陈 · 北口 · 已走 60% · 约 1～2 夜
```

**日志**：

- 出发时记一条
- 抵达 / 遇劫 / 落石等关键事件单独记
- 没有特殊事件的夜晚，只显示在途摘要（避免多队同时运输时刷屏）

## 12. 平衡（Phase C，本阶段不动参数）

**这一轮不要同时大改奖励、体力、马匹消耗和路线距离。**
先让运输循环正确运行，再看数据决定参数。

### 已知风险：马可能才是真正的瓶颈

```
马每趟消耗 14~28（均值 21）
闲置夜自然恢复只有 2
在途期间不恢复

→ 连续三趟长任务：100 → 79 → 58 → 37，跌破 HORSE_LOW=40 触发速度惩罚
```

所以 500 局模拟必须统计：

- 骑手平均体力、受伤率
- **马的平均状态、低状态比例、喂料次数、可用马匹数量**
- 在途任务数量、平均行程夜数
- 派遣数、完成数、超时数、未完成数
- 各路线实际使用比例
