# 变更记录

## 0.5.0 — 2026-11-24

第一个**可以发布给人玩**的版本。这一版的改动全部围绕「玩家能不能理解、
能不能赢、赢了值不值」。

### 结算闭环补强（Round 0.5）

上一轮 v0.4.2 已修遇劫归队保护、遇劫受伤随机流、副作用按任务 ID 顺序执行。
这一轮补上剩下的：

- **混合结算测试断言实际信值**，不再只断言记录顺序。
  用「撞 100 上限」构造两种顺序的差异（不能用撞 0 下限——信归零后剩余
  结算会被中止，两种顺序都停在 0，分不出来）。
- **`advance()` 增加重复 Dispatch ID 检查**：同一封信派两次会抛错。
- **修 `App._autoplay()` 的在途过滤**：原来把在途人马派出去，`advance()`
  抛 `ValueError("还在路上")` 被吞掉，autoplay 静默停在第 1~2 夜。
  现在完整跑 12 夜。

### 拆分 `world_rng`（实验可信度）

原来 `self.rng` 同时负责「世界生成」（天气/预报/信件）和「执行消耗」
（体力/马/油/抵达受伤/采购速度）。

策略改变派单数 → 消耗抽签次数变 → 主随机流错位 → **天气也跟着变**。
于是「同 seed 不同策略」不是严格配对实验。

现在拆出 `world_rng` 专门管世界生成，随存档保存。
新增测试验证：同 seed 两局，一局狂派单一局躺平，前 5 夜的世界必须完全一致。

### AI 策略（Round 1）

- 保留全部原有变体（base / safe / bold / lean / wide / faith）
- 新增 `smart`：编制目标用**总骑手数**而不是可用数，买马前保护添油预算
- 新增 `smart_alt` 作对照：用另一种编制公式，让问题能用数据回答

**八策略对比（各 250 局）的关键结论：**

```
smart       78.0% 达标  S  8.4%   派遣 9.5
safe        77.2% 达标  S 11.2%   派遣 9.4
smart_alt   77.2% 达标  S  7.6%   派遣 9.3
base        28.8% 达标  S  4.4%   派遣 10.5
bold        19.2% 达标  S  1.2%   派遣 10.0
```

1. 两种编制公式结果一样（差 0.8% 在噪声内）——**问题从来不在公式上**
2. 「雇 4 人买 2 马」是保守策略的**结果**，不是吞吐瓶颈
3. **真正的问题是 `safe` 在达标和 S 上同时最优**——冒险在任何维度都不划算

### 平衡：让断崖变缓

原来加急和八百里都是 `slack=0`（零余量），而它们是唯一的高信值来源。
玩家只有两个选择：完全不冒险（S 率 9%），或者接受必挂（达标塌到 30%）。

```
DISPATCH_KINDS["express"]["slack"]   0 → 1
RATING_THRESHOLDS  S 档              80 → 77
```

**500 局实测：**

```
改之前  达标 77.5%  S  9.0%   （另一种打法：达标 30%）
改之后  达标 71.2%  S 27.2%
        评价分布 S=27% A=18% B=26% C=24% D=5% E=0%
```

达标略降是因为 AI 现在**愿意接**八百里了，用风险换信值。
**这就是「让断崖变缓」，不是把难的部分删掉。**

设计目标（评审给定）：达标 65~70%，S 25~30%。

### 游戏内帮助重写

按发布验收要求，帮助页必须让玩家理解四件事，现在分成四小节：

1. **在途占用**——派出的人马不是当夜回来，路程几夜就占用几夜
2. **抵达当夜不能再用**——抵达那夜仍算占用，要等下一夜
3. **天气每夜重算**——不是出发时锁死，预报只有七成准
4. **路上会发生事**——顺风/迷路/落石/遇劫各自的效果

### 发布验收（实机验证）

```

□ 完整推进一夜 + 自动存档     ✅ dist/saves/auto.json 正常写入
□ 优雅关闭（关窗口）          ✅ 退出时存档更新
□ 重启后标题页显示存档        ✅ 「上一局 第 2 夜 信 50」
□ 点「继续」状态完整恢复      ✅ 第 2 夜 / 信 50 / 金 200 / 油 100
□ 帮助页四件事写清楚          ✅ 已截图核对
```

### 待 GPT 复核

## 0.4.2 — 2026-11-24

两位评审对 v0.4.1 的补充。**三处都是「上一轮修得不彻底」。**

### ① 副作用顺序没真正统一（龙娘）

上一轮只把**记录**按 id 排了序：

```python
pending.sort(key=lambda t: id_key(t.dispatch))
result.trips.extend(pending)
```

但**副作用**（faith / gold 的增减）仍按阶段执行——遇劫在阶段②立刻扣信，
抵达在阶段③才加信。所以同一夜里，遇劫永远先于抵达生效，不管 id 谁小。

**实测后果**：id 小的那封本该先送达，却因为 id 大的先遇劫把信扣光，
被记成 `aborted`。记录和效果双双失真。

**改法**：阶段②只标记谁遇劫、把人马记进 `returned_tonight`，不产生效果。
阶段③把「遇劫」和「抵达」放进同一个列表、按 id 排序后依次生效。

### ② 遇劫的人马当夜白拿恢复（龙娘 + 哈基米，两人独立发现）

`returned_tonight` 只收集了 `arrived`，漏了 `robbed`。
遇劫的队伍在阶段②就被移出 `self.trips`，到恢复循环时既不忙、
也不在 `seen_r` 里——于是拿了一份 +35 体力。

**实测**：体力 66.5 一夜回满 100。**遇劫 = 被打了一顿，反而拿休息加成。**

**改法**：遇劫时也把人马加进 `returned_tonight`。

> 哈基米还提到 `expired`（超时抵达）也漏了。**核实后没有**——
> 超时抵达走的是同一个 `arrived` 分支，已经在保护范围内。不需要单独处理。

### ③ 遇劫受伤还在用主随机流（哈基米）

`ROBBERY_INJURY_CHANCE` 和伤期 `randint` 用的是 `self.rng`。
只要局内发生遇劫，开/关事件做 A/B 时后续天气流就会分歧。

**改法**：切到 `self.event_rng`。

### 验证

- 单元测试 73 → **76 项**（新增：遇劫当夜不恢复、副作用按 id 排序、遇劫受伤走 event_rng）
- 确定性：200 组存档往返零分歧
- 300 局平衡：达标 27%，S 4%（和 26% 基本持平——顺序 bug 是边角情况，不影响大样本）

### 平衡现状

```
达标 27%   S 4%   信中位 48
评价: S=4% A=6% B=17% C=33% D=28% E=10%
```

**这是结算正确之后的真实起点。** 按两位评审的意见，下一阶段（Phase C）
先建模拟器指标工具和 AI 策略对照，再动平衡参数。

## 0.4.1 — 2026-11-24

龙娘 v0.4.0 裁决的修订：**只做结算正确性和事件风险定义，不动平衡参数。**

### 结算正确性（P1，五个真 bug）

- **信归零时，已抵达但还没轮到结算的任务会从历史里消失**。
  实测：派出 3 封全部抵达，第一封失败把信打到 0，结果只记录了 1 封。
  这些任务派出去了、资源扣了，却不计入送达率分母——统计虚高。
  现在它们会被记成 `event="aborted"` 并保留。
- **第十二夜最终罚款把信打到 0 之后仍判「守住了」**。
  `_settle_unfinished_on_final_night()` 扣完罚没有重新检查 faith，
  接着无条件 `_finish(True)`。
- **抵达当夜人马提前恢复**。同夜出发+抵达有 `seen_r` 保护，
  但**跨夜抵达**不在 `seen_r` 里，于是抵达当夜白拿一份 +35 体力 / +2 马状态。
  等于路上跑一趟还倒赚体力。
- **遇劫 / 抵达 / 超时三类结果的顺序不统一**。
  遇劫在阶段②追加、抵达在阶段③追加，同一夜的结果顺序取决于哪个阶段先跑。
  现在先把三类结果收集起来，**按 id 数值排序后统一写入**。
- **`TripResult` 缺 `events` 字段**，整趟经历的事件在结算时丢失。
  现在会保留。

### 资源与 UI（P1）

- `GameState.feed()` 禁止喂在途的马（核心层挡，不只靠 UI）
- 商店不再给在途的马放喂料按钮
- 骑手/马列表显示「在途 N%」，头像暗化
- `_assign()` 拒绝在途人马，并给明确提示
- 休息提示排除在途骑手

### 事件模型（P2）

- **落石取消一项惩罚**：只保留「本夜进度归零」，去掉「距离 +1」。
  双重惩罚下实测落石送达率只有 16%——那不是麻烦，是判死。现在 36%。
- **事件概率明确为「每夜」**，换算基数从「出发时的乐观行程」改成
  **「按典型天气的期望行程」**（`expected_nights`）。
- **概率统计复核**（200 局）：

```
每趟至少一次事件：27%（旧模型理论值 29%）
无事 1538 趟    送达率 76%
lost  160 趟    送达率 48%
tailwind 138 趟 送达率 91%
robbery 103 趟  送达率  0%
rockfall 100 趟 送达率 36%
```

### 实验可信度（P2）

- **拆分 RNG**：事件抽样改用独立的 `event_rng`。
  之前事件和其他判定共用一条流，「关掉事件」做 A/B 时整局随机轨迹都会变，
  测出来的差异分不清是事件效果还是随机流错位。
  `event_rng` 也随存档保存。
- 新增三组测试：**结算完整性**（任务不丢、不提前恢复、顺序统一）、
  **真实事件抽样**（每夜率符合换算公式）、**事件流独立性**。

### 这一轮最意外的发现

修完「抵达当夜提前恢复」之后，达标率从 **46% 掉到 26%**。

**之前那 46% 是被这个 bug 抬高的。** 骑手每趟归来白拿 35 体力，
等于出勤率凭空高一截。26% 才是没有这个 bug 时的真实难度。

按龙娘的要求，**本版不动任何平衡参数**。26% 这个数字留到 Phase C 处理。

### 验证

- 单元测试 66 → **73 项**
- 确定性：40 种子 × 5 切点 = 200 组存档往返，零分歧
- 300 局平衡：达标 26%，S 4%，信中位 47

## 0.4.0 — 2026-11-24

在途运输系统的后半程：**B3 存档确定性 + B2 每夜事件**。

### B3 · 存档与确定性

- 修掉一个**静默破坏可复现性**的 bug：所有「按 id 排序」的地方用的是
  **字符串排序**，而 id 形如 `d5 d6 ... d9 d10 ...` ——
  `"d10" < "d9"`，结算顺序在 id 跨过位数边界时会悄悄变。
  结算顺序决定随机数消耗顺序，于是同种子跑两次能得到不同结果。
  新增 `models.id_key()` 按数值排序，所有排序点改用它。
- `SAVE_VERSION` 升到 3，`_migrate()` 处理 v1/v2 升级
- 新增 `tools/verify_determinism.py`：
  - 同种子跑两次一致
  - 第 N 夜存档往返后继续 == 一口气跑完
  - 在途任务进度不丢
  - 读档后在途任务继续推进到抵达
  - RNG 状态精确往返

**验证**：40 种子 × 5 个切点 = 200 组，零分歧。

### B2 · 每夜事件

原来事件按「**每趟**一次」抽。在途模型下改成「**每夜**一次」，
概率必须换算：

```
p_night = 1 - (1 - p_trip) ** (1 / N)      ← 不是 p_trip / N
```

效果重新定义（旧模型「总行程 ±1 夜 / 直接失败」在新模型里不成立）：

| 事件 | 旧模型 | 新模型 |
|---|---|---|
| 顺风 | 总行程 -1 夜 | 本夜进度 ×2.0 |
| 迷路 | 总行程 +1 夜 | 本夜进度 ×0.5 |
| 落石 | 直接失败 | 本夜进度归零 + 该任务距离 +1 |
| 遇劫 | 信丢失 | 信丢失 + 任务立即终止 + 骑手受伤概率 40% |

**顺风必须 ×2.0 而不是 ×1.5**：实测 ×1.5 时，整数夜的边界让顺风
「救不了任何一趟」（2 夜行程本来 2 夜到，加速后还是 2 夜到）。

### 一个我没解决的问题

事件让达标率从 82% 掉到 46%。隔离实验显示：

```
事件照抽但无效果  72.7%
只有顺风有效      74.7%
只有坏事件有效    39.3%
全套              47.3%
```

**坏事件代价 33 个百分点，好事件只补回 8 点。**

我的解释：在途模型下「天气每夜变」和「事件每夜抽」两个随机源
在同一个行程余量上叠加——旧模型只有一个随机源作用于行程。

**详细讨论见 `docs/OPEN_QUESTIONS.md` Q1。这一条比任何数值调整都重要。**

### 验证

- 单元测试 54 → **66 项**
- 确定性：200 组存档往返零分歧
- 300 局平衡：达标 46%，S 14%，信中位 57

## 0.3.0 — 2026-11-24

**外部评审驱动的一轮规则修正。** 两份独立评审（哈基米 / 龙娘）各指出一批问题，
逐条核实后**全部为真**——共 11 项。这一版不增加玩法系统，只保证规则正确。

> 龙娘的原话：「单元测试通过，只能证明代码符合测试写下的规则，
> 不能证明这些规则本身是正确的。」这一版就是去补这句话。

### 规则正确性（第一批）

- **派遣顺序不再影响结果**。这有两层原因：
  1. 灯系数每次现读 `self.oil`，而油在同一夜里边派边扣——先派的那趟看得见，
     后派的那趟就摸黑。实测同一局面只换点击顺序：老陈 2 夜 / 小满 4 夜，
     反过来就是 小满 2 夜 / 老陈 5 夜。
  2. `random` 按派单顺序消耗，`_roll_event()` 抽到顺风还是落石取决于它是第几个。
  修法：灯系数夜初算一次整夜复用 + 进函数先按信 id 排序。
  验证：300 种子 × 4 种油量 × 2 种顺序 = 2400 组，零分歧。
- **信归零后不再继续结算**。原来判定失败之后，剩下的派单照样结算——
  继续扣资源、继续让骑手受伤、日志照常记。现在归零即止，未发出的信退回拒收列表。
- **`faith` 改为整数**。原来浮点累加、日志用 `int(round())` 记差量，两边越走越远：
  实测 6 次送达就差了 2.4 点，复盘时「每一笔都对，加起来不等于总数」。
- **受伤倒计时修正**。原来受伤判定和倒计时在同一个函数里、倒计时在后面无条件遍历，
  抽到「1 夜伤」的当晚就被减到 0 直接痊愈。实测 400 次强制失败：
  36 次保持受伤、**20 次当场就好**——受伤机制有一半失效。
  现在本夜新受伤的骑手不参与倒计时。
- **事件提示不再掩盖失败原因**。原来顺风触发后 `note` 已赋值，后面的超时判断
  `if not note:` 永远不执行，日志写着「顺风，快了一夜」而信其实没送到。
  现在事件和结果分开记，且「晚了一夜」改成「晚了 N 夜」。

### 系统完整（第二批）

- **修路功能接上 UI**。`repair_route()` 之前只有实现、没有入口，是纯死代码——
  玩家永远触发不到。现在整备面板里有三条路的修缮按钮（每条只能修一次）。
- **天气预报当场反馈**。`forecast_was_right` 之前只在结算日志里用，
  游戏过程中完全不告诉玩家预报准不准。而「预报七成准」正是信息核心，
  玩家却永远学不到它准到什么程度。现在预报错了当场在日志里说明。
- **休息改为自动推断**。`advance()` 不再要求调用方传 `resting` 列表——
  本夜没被指派、没受伤的骑手自动算作休息。原来只要 UI 或测试漏传一次，
  就会出现「站着发呆一整晚却不回体力」。
- **出勤的马不再吃自然恢复**。原来无条件遍历所有马 +2，跑完任务的也加，
  和 README 写的「不跑也会自己回一点」不符。
- **两个模拟器统一**。`sim_balance.py` 和 `ai_optimal.py` 原本各写一套策略，
  且都调用不传天气的 `travel_nights()`（等于用真实天气决策，偷看答案）。
  现在共用 `tools/ai.py`，且只看预报。
- **存档 / 读档**。三个手动槽 + 一个自动槽，每夜自动存、关窗口也存。
  `from_dict()` 里把模块级 id 计数器推到已有 id 之上——否则读档后新雇的人会撞号。

### 文档

- `balance.py` 里 `WEATHER_SCHEDULE` 的注释原来写成「取第一个 <= 当前夜」，
  实现取的是最后一个。行为是对的，注释在误导人——已改。

### 验证

- 单元测试 25 → **38 项**，新增的 13 项专门盯着上面这些边界
- 300 局模拟：达标 70%，S 40%，信中位 74
- 顺序无关性：2400 组对比零分歧
- 存档往返：所有字段一致、无 id 撞号、能继续打、坏档不崩

### 诚实记录：一个没能解决的问题

策略搜索显示「**只接有余量的**」（`min_margin=1`，完全不冒险）比基准打法
S 率高 14 个百分点（57.3% vs 43.3%）、达标率高 26 个百分点（95.3% vs 68.7%）。

**也就是说这个游戏目前奖励纯保守——「赌预报」这个核心机制是不划算的。**

根因可能与「行程夜数是假的」有关（见 ROADMAP 第 1 条）：如果一趟 2 夜的行程
真的占用骑手 2 个回合，长路线的稳定性就要付人力代价，无风险策略的优势会被削弱。

## 0.2.0 — 2026-11-23

「打满一局之后才发现的问题」专项修复。0.1.0 的问题是：**从没有人真正完整玩过 12 夜**，
所以所有「只在完整对局里才浮现」的缺陷都留到了玩家手上。

### 核心平衡（全部由实测驱动）

- **`FAITH_PER_DELIVER` 2.0 → 2.8**。原值下只读预报认真打，达标率仅 41%、S 率 12%——
  每个决定都做对也只有四成能守住，S 基本靠运气。新值：达标 73%、S 38%。
- **遇劫罚则减半**。原来八百里遇劫一次 -20 信（总信量的 1/4），而触发概率只有 5%。
  一次骰子就能抹掉四夜的进度——那不是难度，是方差。现在扣一半（-7~10）。
- **马每夜自然恢复 +2**。原来马不喂就永远停在低值，玩家会在第 6 夜左右突然发现
  「全员瘫痪」且不知道该怎么补救。实测这个改动几乎不影响难度曲线（S 率 37%→39%），
  纯粹是给失误留一条自救路径。
- **评价档位补齐 D（20–40）、E（0–20）**。原来 15 信和 40 信都是 C。

### 界面

- **修掉信息泄漏**：「预计 N 夜」原来用**真实天气**算，等于在派出去之前就告诉玩家
  一定能赶上——GDD 里写的「赌预报」根本不存在。现在用预报算，并对天气敏感的路
  额外标「变天则误」。
- **信条加三条刻度**：守（60）/ A（70）/ S（80）。原来看不出 S 线在哪。
- **日志从 4 行扩到 7 行**，标题「昨夜」→「近况」。打到第 9 夜时已经记不清第 5 夜了。
- **加「清空本夜」按钮**。误点后只能逐个取消，很容易点错。
- **加休息提示**：「歇着：某某（体力 +35/夜）」＋「马不跑也会自己回 +2/夜」。
  原来看不出「什么都不派 = 休息」。
- **整备面板加 × 关闭按钮**（点面板外也行）。原来只认 Esc，纯鼠标玩家会卡死在面板里。

### 工具

- **修掉评测工具的信息泄漏**：`tools/sim_balance.py` 的 AI 也调用了不传天气的
  `travel_nights()`，即用真实天气决策——相当于作弊，测出的难度比玩家实际面对的
  偏低约 8 个百分点（通关 81% vs 73%）。现在统一用 `gs.forecast`。
- 新增 `tools/ai_optimal.py`：策略搜索器，可扫多组参数找最优打法。
- 新增 `tools/play_seed17.py`：按预计算序列自动操作，用于回归验证。

### 验证

- 25 个单元测试全过
- 400 局模拟：通关 73%，S 38%，信中位 74
- **手动打满一局拿到 S**：种子 17，信 83，送达率 89%（16/18），逐夜决策见
  `logs/run-*-win.txt`

## 0.1.0 — 2026-11-23

首个可玩版本。

### 核心

- 十二夜回合制循环：黄昏收信 → 排班 → 夜间模拟 → 黎明结算 → 整备
- 三名资源：信（失败线）、金、油
- 三条路线，各自的天气抗性不同（北口怕雪、河渡怕雨、矿道免疫天气）
- 五种天气，随夜幕推进恶化
- **天气预报只有 70% 准确** —— 整个游戏的信息核心
- 骑手体力 / 马匹状态的双重消耗，逼出轮换与预算选择
- 五类夜间事件（顺风 / 迷路 / 落石 / 遇劫 / 无事），概率受天气调制
- 三种信件（寻常 / 加急 / 八百里），期限由路线基准夜数推导
- 商店：雇骑手、买马、喂料、添油、修路（每条路只能修一次）
- 胜负判定 + S/A/B/C 评价

### 画面

- 1280×720，pygame-ce
- 20 张美术素材，本机 ComfyUI + RealVisXL 生成
  - 标题 / 主背景 / 两种结局
  - 三条路线立绘
  - 五种天气图标
  - 四张骑手立绘、两张马立绘
  - 纸纹 / 漆木纹
- 程序化飘雪（三层视差）、灯火余烬、震屏
- 水彩 + 水墨的美术方向，冷靛蓝 + 暖琥珀

### 声音

### 工程

- 核心逻辑与渲染完全分离，`relay/core/` 不 import pygame

### 验收后修的 bug（同日）

真机 GUI 完整跑过一遍后发现并修复：

1. **躺平可过关** —— 十二夜全不派信，仍判「撑过了十二夜」。
   破坏性最强的一个：最优解变成「什么都不做」。
   修法：`total == 0` 时一律判负，结局文案「十二夜过去了，你一封也没派出去。」
2. **整备面板排版** —— 按钮名居中、价格右对齐，两者撞在一起；面板底部大片空白。
   修法：名字左对齐、价格右对齐，面板高度跟内容走。
3. **标题页残留文案** —— 底部写着「每夜只能问十二次以内的事」（从别的项目抄过来的）。
4. **「怎么玩」按钮不可见** —— ghost 样式在亮雪地上几乎透明，改成 normal。
5. **送达率 0/0 显示 0%** —— 一封信没派时应该显示「—」。
